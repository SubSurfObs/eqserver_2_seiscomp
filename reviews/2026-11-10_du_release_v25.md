# Review: DU release v2.5 overlap and planner fixes  (2026-11-10, reviewer: Codex)

## Verdict

FIX-THEN-PROCEED.

The central earliest-start rule is implemented correctly, but two targeted
waveform defects remain: LKHRT samples are shifted by 4 ms during the final
trace-joining step, and BLAT source samples that begin just before their
filename minute are still clipped. Hold those affected units. Fix each defect
and rerun only its existing proof day; another campaign or broad station sweep
is not warranted.

## Findings

### F1 — blocker — final trace joining shifts LKHRT samples onto the wrong time grid

- Where: `scan/phase3_driver.py:1061-1090`;
  `~/v3_test/es/LKHRT.2023/audit_2023-10-27.json`; staged HHN/HHZ day 300
  files under `~/v3_test/es/LKHRT.2023/sds/2023/DU/LKHRT/`.
- Status: verified.
- Scenario: the new in-file overlay correctly retains an off-grid packet on
  its stated grid. Later, `_coalesce_pieces` joins any piece whose start is
  within half a sample of the current run's continuation and then keeps only
  the first run's timestamp. At 100 Hz, a retained LKHRT source segment starts
  at `.125`, but the written trace places that segment on a grid anchored at
  `.121`: a real 4 ms (0.4-sample) shift. The output around 05:06 has HHZ
  traces ending at `05:06:21.105` and starting at `05:06:21.121`; the source
  packet's surviving grid is `.125`. The independent audit consequently finds
  3,420 HHN and 3,475 HHZ samples for which no source copy agrees, plus a
  topology break of +0.60 sample. This is an output weld/timing error, not an
  auditor artefact, and it contradicts the rule that retained samples keep
  their stated times.
- Smallest fix or check: never coalesce pieces with a non-zero grid phase. If
  miniSEED readers would weld two traces separated by less than half a sample,
  discard only the minimum boundary sample needed to make the new source grid
  independently representable, record that loss, and keep every remaining
  sample at its exact source timestamp. Add an end-to-end write/read regression
  for the `.121`/`.125` case; the current in-memory overlay test cannot see the
  later coalescing defect. Rerun only LKHRT 2023-10-27 and require zero wrong
  samples and no unsupported topology span.

### F2 — blocker — BLAT decisions still discard samples before the filename minute

- Where: `scan/coverage_planner.py:560-574`;
  `~/v3_test/es/BLAT.2023/sel.sqlite`;
  `~/v3_test/es/BLAT.2023/audit_2023-10-30.json`; source file
  `20231030_0232_BLAT.ms.zip`.
- Status: verified.
- Scenario: the planner authorizes the 02:32 file from exactly 02:32:00, but
  its E/N/O traces start at 02:31:57.227 and its Z trace at 02:31:57.307.
  Those real samples are clipped before the resolver sees them. The same shape
  repeats at minute boundaries across the day. The audit finds zero wrong
  values but 192.09 channel-seconds present in source and absent from output:
  52.07 E, 51.77 N, 50.65 O and 37.60 Z. On this sparse proof day that is about
  2.2% of available channel-time, below Dan's greater-than-99% recovery target;
  it is not an unexplained source outage.
- Smallest fix or check: have a fully probed file's authorization begin at its
  measured earliest sample time, not only its filename minute. Persisting the
  measured header interval is the precise solution; a bounded leading read
  grace is also safe because a file can contribute only samples it actually
  contains and the resolver already prevents overwrite. Recompile BLAT and
  rerun only 2023-10-30. Do not promote BLAT while this systematic loss remains.

### F3 — should-fix — the detailed precedence evidence is not preserved by promotion

- Where: `scan/phase3_driver.py:1274-1289`, `scan/phase3_driver.py:2280-2284`;
  `../sds_staging_ledger/apply.py:393-400`;
  `scan/run_production_promote.py:104-125`.
- Status: verified.
- Scenario: v2.5 writes every displaced interval to
  `<run-manifest>.precedence.jsonl.gz`, while the JSON manifest stores an
  absolute staging path and a content hash. The proof sidecars are internally
  consistent: all six hashes and manifest totals checked, including 4,129,692
  displaced samples for LKHRT 2023. But `apply.py` copies only the JSON manifest
  into the permanent ledger run record, and the promoter neither validates nor
  copies the sidecar. Queue cleanup or relocation would therefore leave the
  permanent record pointing at a missing staging file.
- Smallest fix or check: without reconverting anything, copy the sidecar into
  the permanent run-record directory (or another durable provenance archive),
  verify its content hash, and store a durable relative reference. Until that
  is implemented, at minimum archive each s5 sidecar and verify its hash before
  deleting or moving a queue.

### F4 — should-fix — the commit-time release guard omits the conversion engine

- Where: `scan/phase3_driver.py:1826-1831`,
  `scan/phase3_driver.py:1878-1883`; `scan/test_header_names.py:257-262`.
- Status: verified.
- Scenario: the run manifest records three code identities, but the
  commit-time unknown-identity check passes only `eqserver` and `sudspy` to
  `release_identity_gaps`. If `git rev-parse` fails for `disk_to_sds`, a
  committed manifest can still contain `disk_to_sds: "?"`. The current s5
  TPSOP manifest has all three valid hashes, so this is a guard gap rather than
  evidence that the current run was unpinned.
- Smallest fix or check: include `disk_to_sds: engine_sha` in that check and
  make the regression require all three named keys. No waveform rerun is
  needed.

### F5 — should-fix — the first full TPSOP 2017 run is safely held on one corrupt-source day

- Where:
  `/mnt/seiscomp_staging/eqserver_sweep_du_v2_rebuild_s5/convert_failed.jsonl`;
  run manifest `eqserver_DU_TPSOP_2017_20261109T213555Z.json`, day
  2017-11-09.
- Status: verified.
- Scenario: the full run produced no `convert_done` event. Day 2017-11-09 is
  `qc_flagged` because the 13:52 and 13:53 `.relay.ms.zip` files contain
  invalid miniSEED times. A readable 13:52 `.relay.ms.gz` alternative exists;
  no corresponding 13:53 alternative was found. The wrapper correctly records
  the unit as failed, so this has not silently entered the promotion set.
- Smallest fix or check: audit only those two minutes. Confirm the readable
  13:52 copy filled every available sample, then quantify whether 13:53 is
  genuinely unrecoverable or covered by another authorized file. If it is
  genuine source corruption, record an explicit operator acceptance under the
  existing corrupt-source policy; otherwise fix the missed alternative. This
  is not a reason to rerun unrelated stations.

## Checked and found OK

- The earliest-start overlay itself follows the requested rule: stated-start
  ordering, deterministic equal-start tie, half-open occupation, exact integer
  nanoseconds, retained samples on their own grids, and loud failure for
  overlapping different rates. The auditor implements its own equivalent view
  rather than importing the converter's function.
- The resolver's revised end index retains only samples whose complete
  half-open span ends before the next occupied span. This closes the previous
  off-grid overlap without moving samples.
- Once size evidence proves a small population-month mixed, the planner now
  reads the remaining files individually. This recovered BLAT's normal-sized
  four-channel files and raised the proof day from roughly 31% to roughly 98%
  with no wrong values. F2 is the remaining start-window defect, not a failure
  of the per-file channel census.
- A file with a read error but no unknown channel no longer blocks its whole
  day. LKHRT 2023-06-28 converts the readable files, records the damaged file,
  and has zero wrong samples. Unknown channel labels still block.
- The targeted proof days for TPSOP, LILH and the other LKHRT days contain no
  wrong samples. The remaining missing intervals are small and explicitly
  reported rather than hidden.
- The MVM1Y plan now explicitly enumerates both its 100 Hz `EH*` and 250 Hz
  `DH*` output identities, closing the previous plan-contract finding.
- The backfill preserves the original conversion-time selection path on a
  repeat repair. A read-only verifier found no bad release identity, missing
  selection or wrong rebuild selection among the completed rebuild records it
  checked; the remaining manifests with `sudspy: "?"` belong to non-completed,
  superseded runs and cannot be promoted through `convert_done`.
- The reviewed diff adds no origin-archive write, long-term write, plan-gate
  bypass or uncommitted-code production path.
