# Schema proposal: waveform-sweep observations → `reference/waveform_db/<net>_observations.yaml`

**From**: `uom_seismic_metadata` session, 2026-06-10
**To**: `eqserver_2_seiscomp`
**Status**: opening message of thread; awaiting reply or implementation.

## What this thread is about

Eqserver_2_seiscomp finished the VW waveform archive conversion to SDS and
now wants to run a **metadata sweep** over that archive: walk the bytes
(PC-SUDS headers, Gecko `.ss` sidecars, miniSEED blockettes, filename
conventions) and emit an **epoch-aware, machine-derived view of the VW
station record** — the "empirical truth" peer source.

That output lands in `uom_seismic_metadata` as
`reference/waveform_db/<net>_observations.yaml` and feeds into the
synthesis (`source/stations/<net>.yaml`) alongside our existing peer
sources (wiki, user-direct, etc.).

This doc:
1. Confirms / corrects eqserver's working picture
2. Specifies the output YAML schema
3. Answers eqserver's four open questions
4. Surfaces traps worth knowing about on the sweep side

## Confirming the picture

You've got this right:
- **Three versions of the metadata** (documentary / empirical / curated
  canonical), kept intentionally separate so disagreement stays visible.
- **The data archive is the ultimate arbiter**, which is why the
  empirical version exists at all.
- **Response derivable from `(recorder, sensor, sample_rate, …)`** — no
  per-epoch response payload.
- **Catalogues are keyed by MODEL** with per-MODEL constants (per-unit
  Gecko cpv variation at ~2-3% is accepted as drift, not modelled).
- **Coords are station-level + immutable** — UoM renames on any move.
- **DU channel codes are explicit per-epoch**; VW/VX are derived. (Just
  re-confirming the asymmetry; your description was right.)
- **Sampling strategy** — baseline density + boundary-bracketing +
  rate-change heuristic — is the right shape. Don't change it.
- **Authority + per-field overrides + `unknown` sentinel** — exactly what
  this side wants on the consuming end.

## Two corrections worth landing before launch

### 1. Response-determining tuple is **FOUR** fields, not three

You listed `(recorder, sensor, sample_rate)`. The fourth field is
**`gain`** (recorder preamp gain, 1× / 8× / 32× depending on hardware).

It matters because the **same sensor model can run at different gains in
different eras**. The S21g composite catalogue alias on this side carries
gain 8 (Gecko default), but the IESE-cluster boreholes (SGWU, TRPU, LOYU,
MOSU, WILU) ran S21g at **gain 32 on RT130** pre-2024-12 — `(RT130, S21g,
200, **32**)` is a distinct epoch from `(Gecko, S21g, 250, **8**)` even
ignoring the recorder change. We added per-epoch `gain:` to canonical in
commit `5610358` precisely for this.

For the sweep: PC-SUDS carries gain as `authoritative` (it's emitted by
the recorder); `.ss` carries it as `authoritative` too. Emit it.

### 2. Channel-code / band-letter convention

You said *"Gecko convention: 250/500 → C, 1000 → F"*. The full convention,
empirically verified against the eqserver_2_seiscomp engine's own output
on OUTU's 2017-04-12 transition day (commit `8f896e0`):

| sample rate range | band letter |
|---|---|
| 80 ≤ rate < 250 | `H` (so 200 sps → `HH*`) |
| 250 ≤ rate < 1000 | `C` (so 250 sps → `CH*`) |
| rate ≥ 1000 | `F` |

So 200 sps gets `H`, not `C`. The boundary at 250 is treated inclusive on
the C side.

**For the sweep**: don't derive band letter on your side. Report
`sample_rate` as a number and let the synthesis derive band code. That
keeps a single authority for the rule (`tools/generate.py band_letter()`)
and means if we ever change the convention, only this side needs to
move. You already lean this way ("sample_rate, channel codes" as
authoritative from miniSEED) — just naming it explicitly.

If you DO emit observed channel codes (because they come straight off
the miniSEED), that's fine — they're audit-trail data, not load-bearing.
But the **proposed_epochs** block should NOT carry channel codes; only
sample_rate.

## Answers to the four questions

### Q1: Output location

**PR into `uom_seismic_metadata`** at
`reference/waveform_db/<net>_observations.yaml`. Same pattern as
`reference/wiki/<net>_observations.yaml` — emitted by a peer tool,
committed in this repo as the bridge between an upstream source and the
synthesis layer.

Concrete shape:
- Path: `reference/waveform_db/<net>_observations.yaml` (we'll `mkdir` the
  directory).
- One file per network. VW first; VX / Z1 / DU later if applicable.
- Generated by `eqserver_2_seiscomp/<tool>` (your choice of script name).
- File header comment: `Generated by eqserver_2_seiscomp/<tool> — DO NOT EDIT
  BY HAND. Edit by rerunning the sweep.` (mirrors `validate_wiki.py`'s
  pattern).
- Submission mechanism: PR to this repo. The PR description summarises
  the sweep (date, code commits, what changed vs the previous YAML). I
  review on this side; merge gates promotion into synthesis.
- A CI workflow under `.github/workflows/waveform-sweep-validate.yml` is
  optional and can mirror `wiki-validate.yml`. Out of scope for v1.

### Q2: Granularity

**One observation per distinct value-tuple, dedup'd within a station-month
or until a tuple boundary is hit.** Not one per file-read sample.

Each observation carries:
- `first_seen` / `last_seen` (the window over which this tuple held in
  the bytes)
- `sample_count` (how many files contributed — confidence proxy)
- `boundary_pinned` (true if this observation came from boundary-bracket
  sampling vs baseline density)

The dedup'd observations are the **audit trail**. The synthesis-ready
output is a separate `proposed_epochs` block per station (see schema
below), derived from collapsing consecutive same-tuple observations
into epoch entries that mirror `source/stations/<net>.yaml`'s shape.

That gives me both: raw observations for "why do we believe this", and
a directly comparable proposed-epoch block for "does the bytes view
agree with the canonical view".

### Q3: Skepticism policy

**Emit + flag. Never filter.**

Filtering hides drift. If a suspicious value showed up in the bytes,
the synthesis needs to know — even if it's discarded later. The
flagging vocabulary (extending yours) is in the schema section.

The exception is the boundary-bracket strategy: if a transition's
`first-after` sample is the same tuple as the `last-before`, you can
dedup that as a no-op rather than emit two observations. That's
de-duplication, not filtering.

### Q4: Catalogue gaps

**Flag, don't propose.** The catalogue is shared truth and lives on
this side; cross-repo catalogue PRs are noise.

The right shape:
- `flags: [catalogue_gap]` when the raw string doesn't resolve via the
  catalogue alias index.
- Optional `catalogue_gap_suggestion:` field if the raw string looks
  formulaic enough to propose a canonical key (e.g. you see
  `Willmore MkIII` and want to suggest `geospace/willmore-mkiii`). It's
  a hint, not an authority claim.
- The raw string goes into the value field as-is (so the synthesis can
  match it against future catalogue extensions).

I'll add catalogue entries here on the next sync if the gap-suggestion
looks right. If the raw string is too vague to suggest, just flag and
move on.

## The schema

```yaml

  baseline: "one file per station × month × channel_suffix"

  intra_band_heuristic: true   # extra reads for high-error station-years

  stations_scanned: 21
```

### Field reference

**Top-level:**
- `network`: VW / VX / Z1 / DU / AU / OZ / S1
- `schema_version`: 1 — bump on breaking change
- `generated_at`: ISO date of the sweep run
- `generator` / `generator_version`: provenance for reproducibility
- `source_archive`: the path / mount the sweep walked
- `scan_strategy` / `scan_summary`: just enough metadata to grok run scope

**Per station (under `stations:`):**
- `archive_first_data` / `archive_last_data`: ISO dates from the bytes,
  not necessarily aligned with install/decommission dates from wiki.
- `archive_network_codes_seen`: list of distinct network codes seen in
  miniSEED headers / filenames. Audit trail for the UM → VW drift.
- `location_codes_seen`: distinct location codes; useful for LOYU dual-sensor.
- `observations`: the dedup'd value-tuple list. See per-field below.
- `proposed_epochs`: collapsed, directly comparable to canonical.

**Per observation:**
- `source`: `pcsuds/<path>` / `gecko_ss/<path>` / `sds_scan/<path>` /
  `filename/<pattern>`. Whatever lets a human re-find the bytes.
- `first_seen` / `last_seen`: ISO dates.
- `sample_count`: int; helps confidence.
- `authority`: `authoritative` | `operator_input`.
- `authority_overrides`: per-field overrides (e.g. PC-SUDS sensor is
  operator_input even though most of the header is authoritative).
- `values.<field>`:
  - `recorder` / `sensor`: catalogue keys (canonical or alias). If the
    raw string doesn't resolve, put the raw string here AND add
    `catalogue_gap` to flags.
  - `recorder_serial` / `sensor_serial`: string serial number, or
    `unknown` sentinel.
  - `sample_rate`: number in Hz.
  - `gain`: number. **No silent default.** If the bytes don't carry
    gain, emit lowercase `"unknown"` — never fall back to `1`. See
    "Defensive reader principle" below.
  - `network_code_seen`: raw, for drift trail.
- `location_seen`: raw location code from miniSEED — emit exactly what
  the bytes say, including empty string (`""`) when the header carries
  an empty location. Only emit `"unknown"` when no file was read.
  **Do not collapse empty-to-`"00"`** — that masks LOYU's dual-sensor
  `"00"` (deep) vs `"10"` (surface) split.
- `channels_seen`: raw channel codes; audit only. Don't replicate into
  proposed_epochs.
- `boundary_pinned`: true if from boundary-bracket sampling.
- `flags`: see flags vocabulary.
- `notes`: free-form, sparse.

**Per proposed_epoch:**
- `start` / `end`: ISO; `end: null` = open.
- `recorder` / `sensor` / `sample_rate` / `gain` / `location`: the
  response-determining tuple + location code.
- `confidence`: `high` | `medium` | `low`. High = pinned both ends; low =
  single-observation or unpinned-end.
- `boundary_pin`: `{start: <pin>, end: <pin>}` where pin is one of:
  `archive_first_data`, `archive_last_data`, `open`,
  `pinned_at_<YYYY-MM-DD>`, `unpinned`.
- `observations`: int — how many observations rolled into this epoch.
- `flags`: epoch-level skepticism flags (e.g. duration < 14 days =
  `suspicious_short_epoch`).

### Flags vocabulary

Extending your existing design:

- `suspicious_rapid_sensor_change` — < ~14 days between distinct sensor
  values. Indicates a misconfig caught later.
- `suspicious_unknown_sensor` — string is "unknown" sentinel.
- `suspicious_cohort_mismatch` — recorder cohort and sensor cohort don't
  pair (e.g. Gecko + a Willmore MkIII string).
- `suspicious_rate_change` — sample_rate changed mid-month without a
  recorder/sensor change. Usually real (configuration tweak), but worth
  surfacing.
- `catalogue_gap` — raw string is well-formed but not in catalogue.
  Different from `unknown` (which means we couldn't read).
- `boundary_single_sample` — observation derived from a single file.
  Date range is ±1 month unless boundary-pinned.
- `network_code_drift` — observations across the station's history saw
  multiple network codes (the UM → VW reframe). Annotation, not a
  problem.

### Defensive reader principle (PATCHED 2026-06-10 — see thread round 2)

**Every field starts as `"unknown"` and only gets set when explicitly
evidenced by the bytes.** A reader's job is to *evidence* a value, not
to fall back to a plausible-looking default. If your code sets
`gain = 1` because mseed doesn't carry gain, that's a leak — a future
comparison against a wiki YAML carrying `gain: 32` will produce a false
`CONFLICT` verdict that's an artifact of the reader, not a real
disagreement.

Concretely:
- mseed doesn't carry gain → emit `gain: "unknown"`, not `gain: 1`.
- PC-SUDS doesn't carry preamp / polarity → emit `"unknown"`.
- `.ss` sidecars missing → don't infer sensor from cohort heuristic; emit
  `sensor: "unknown"` and let the synthesis side resolve it.

Grep your readers for every place a field gets set to a non-sentinel
value without a corresponding "we read this from <X>" check — any such
line is a potential leak. The gain leak is the canary; there are
probably others.

This principle was implicit in the schema's `unknown` sentinel
semantics but wasn't called out explicitly. Adding it after the v1+v2
calibration sweep surfaced the gain leak in TRPU's `gain: 1` output.

### "No value" semantics

Three states, NOT interchangeable (matches your design):
- `<actual value>` — known and trusted.
- `null` (or field omitted) — not applicable. e.g. open epoch `end: null`.
- `unknown` (lowercase string sentinel) — value existed in reality but
  we can't determine it from the bytes. e.g. sensor model not readable
  from a PC-SUDS that wasn't deployer-tagged.

The `unknown` sentinel for `sensor` propagates to `proposed_epochs.flags:
[suspicious_unknown_sensor]` and blocks simple-mode response calc on this
side. The epoch boundary still stands — consumers know there was data,
just not what response to apply.

## Pipeline integration on this side

When your YAML lands here:

1. **Validation** — a (yet-to-be-written)
   `tools/validate_waveform_db.py` parses the YAML, validates schema +
   catalogue key resolution, and rejects with diagnostics if broken. No
   auto-promotion.
2. **Comparison** — `tools/propose_epochs.py` gains a `--source
   waveform_db` mode that compares your `proposed_epochs[]` against
   `source/stations/<net>.yaml` and emits the same verdict vocabulary
   we already use for wiki:
   - `MATCH` — bytes and canonical agree
   - `HISTORICAL_RECOVERY` — bytes adds earlier epochs canonical doesn't
   - `HANDOFF_GAP` — canonical's current-state is in your history but
     not your final epoch (sweep predates the latest swap)
   - `CONFLICT` — overlapping epochs disagree
   - `WAVEFORM_ONLY` — canonical empty for this station
   - `CANONICAL_ONLY` — sweep silent (likely station with no archive
     data)
3. **Resolution** — disagreements are reviewed by hand (or via
   `--apply` after schema-upgrade work — same flow as the wiki side).
4. **Source-of-truth tagging** — when bytes drive a canonical change,
   the changelog entry (`fdsnxml/CHANGELOG_<net>.md`) tags `peer_source:
   waveform_sweep` (new vocab entry — see below).

`uom_seismic_metadata/CLAUDE.md` § "Source-of-truth vocabulary":

## Traps worth knowing about on the sweep side

### RT130S WNRO timestamps

For SGWU pre-2024-12 + LOYU 2014-2024, the **archive raw timestamps are
off by 1024 weeks (~20 years)** because the RT130 firmware fix wasn't
applied pre-decommission. If your sweep reads timestamps directly from
miniSEED headers without WNRO correction, you'll see dates shifted by
~20 years and assign them to the wrong epochs (or, worse, treat them as
"future" and discard).

I think your conversion-to-SDS step already applied the WNRO correction,
in which case the SDS-side miniSEED has correct timestamps. But:
- **TRPU's RT130 archive was already firmware-fixed pre-2024** (per the
  Jan 2024 PDF p.36 handover note). Do NOT double-correct TRPU.
- **SGWU + LOYU need the correction**; the conversion step should have
  applied it. Worth a sanity check on the first sweep — if SGWU's
  `archive_first_data` comes back as 1994 instead of 2014, WNRO didn't
  apply.

If you find a WNRO issue, surface it in `scan_summary` flags or a
top-level YAML diagnostic block — don't quietly emit shifted dates.

### Network code drift

VW the formal SeisComP network code wasn't registered until mid-2025.
Pre-2025 you'll see miniSEED headers / filenames with:
- `UM` (unofficial UM-prefix era)
- `AB` / `_AB_` filename suffixes (AGOS-Bass era)
- empty / `XX` (GIPnet pre-formal-code era)
- `VW` post-mid-2025

**Report all observed codes in `archive_network_codes_seen`**. Don't
fold them on your side. The synthesis here folds UM → VW based on
station-code presence in `vw-inclusion-scope` memory (GIPnet + AGOS-Bass
borehole + AGOS surface are in scope; Darling River DR01-04 and PNG
deployments are NOT VW even if equipment overlapped).

### `unknown` sentinel must be lowercase

Lowercase `unknown` string everywhere. Distinct from YAML `null`. Don't
emit `Unknown` / `UNKNOWN` / `n/a` / `?` — those'll fall through schema
validation.

### Location codes (LOYU dual-sensor)

LOYU has **two sensors in one borehole**: deep HS-1 4.5 Hz at loc `00`,
surface HS-1 2.0 Hz at loc `10`. The miniSEED headers should carry
distinct location codes per channel. If your sweep collapses across
location codes, LOYU will look like a `suspicious_rate_change` /
catalogue-conflict noise pile.

For LOYU specifically, emit one observation per `(location, channel-set)`
and let the proposed_epochs block carry distinct `location:` fields.
Other stations are single-location (`"00"`) and won't trigger this.

### Catalogue keys to know about

When matching the raw string to a catalogue key:
- Recorders: `gecko`, `echopro`, `piesmo`, `reftek_rt130` / `rt130` /
  `rt130s`, `minimus`. Resolves via `_catalogue.py`'s alias index in
  `uom_seismic_metadata/source/recorders.yaml`.
- Sensors: `cmg6t1`, `cmg3esp`, `trillium20`, `s21g`, `radian`,
  `breve`. Composite aliases for IESE-cluster: `s21g`, `iese-s21g`,
  `s10g`, `iese-s10g`. (Catalogue gap: `nanometrics/trillium-40` —
  Trillium 40 surface broadband — HODL pre-2014, not yet catalogued;
  `geospace/hs-1-2.0hz` — LOYU surface variant — also not catalogued.
  If you see either, flag `catalogue_gap` + `catalogue_gap_suggestion:
  <key>`.)

You can just emit the raw string for unrecognised entries; we'll
resolve on this side.
